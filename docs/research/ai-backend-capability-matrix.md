# AI backend capability matrix

**Reviewed:** 2026-10-14

**Purpose:** Keep direct model APIs, multi-step coding-agent runtimes, and speech synthesis as separate choices. This matrix distinguishes routes present in source from routes that have passed the full acceptance contract.

**Implementation snapshot (2026-10-14):** `rig-core = 0.44.0` is pinned. Gemini, OpenAI Responses, and Anthropic Messages can be explicitly selected for file chapters, optional repository orientation, selective section regeneration, PR Guides, transient single-hunk PR change explanations, and a distinct range-scoped Code Lens explanation. Their local review binds provider, model, sanitized endpoint, encoded JSON body/hash, selected context, and disclosure version. PR change explanations rebuild one selected local file/hunk from immutable base/head refs, display and send only that hunk, return bounded side-aware claims with exact hunk citations, and do not create PR Guide history or alter Git refs. The Code Lens route accepts only a hash-verified inclusive line range and optional exact UTF-8 byte span from the immutable snapshot, caps the excerpt at 32 KB, screens the selected bytes for secret-like content, and returns only bounded claims with exact in-range citations; it does not create a chapter or affect coverage. A guarded Reqwest transport checks that the method, route, authentication placeholder, content type, and body match review before using the provider-specific sensitive auth header; requests require HTTPS and are unary. Offline Rust fixtures verify selected-provider review routes and encoded bodies for all three adapters across file chapters, orientation, section regeneration, PR Guides, Code Lens, and PR change explanations. Both transient explanation routes require complete consent, validate returned citations locally, and have no provider fallback. Provider eligibility, production HTTP and provider-specific HTTP error mapping, remaining operation-by-provider error/no-fallback and history fixtures, and cancellation/connection-close evidence remain open.

## Status legend

- **Implemented · fixture gate open:** a selectable route exists in source for this operation/provider, but required mocked routing and capability evidence is incomplete, so it is not marked accepted support.
- **Not implemented as a distinct operation:** no operation-specific route exists, even if another workflow can be launched from the same screen.
- **Candidate · unverified:** evaluate this backend; no app-supported route exists yet.
- **Unavailable until verified:** do not show as selectable for that operation until the exact version, auth/terms, capability boundary, and fixture acceptance are recorded.
- **Supported:** may be used only after the corresponding acceptance evidence is linked here. No cell currently has enough evidence to carry this status under the full matrix contract.

For every cell promoted to **Supported**, the catalog must record the pinned adapter/library and provider/model surface; schema, streaming, cancellation, endpoint, authentication, terms, usage disclosure, and data handling; a mocked fixture for the operation; exact-provider routing; consent fingerprint invalidation; and error behavior. An unsupported feature must be shown before send. No key, prompt, source excerpt, or raw response is written to logs, local metadata, exports, or diagnostics.

The source now routes all three direct APIs through Rig's provider-specific unary adapters and the same exact-review boundary. The app catalog contains structured-output and provider streaming flags, but the current transport explicitly rejects streaming; per-operation streaming/cancellation support is therefore not selectable capability evidence. Rust formatting, a library compile check, and a frontend production build succeeded for this snapshot. They do not prove endpoint behavior, provider eligibility, provider-by-operation mock routing for Code Lens, credential non-disclosure, or cancellation closing the HTTP transport. No live API key or request was used.

Coding-agent sessions are distinct from direct API calls. Candidate names do not imply account eligibility, official programmatic access, or a safe read-only boundary.

For each workflow/runtime pair, the versioned compatibility record must state **supported** or **unavailable with a reason**. An agent receives only reviewed immutable staged files, no `.git`, live checkout, shell/build execution, unrelated MCP tools, or outside paths. If documented permissions cannot prove that boundary, the runtime stays unavailable. Output is untrusted and must pass local schema and source-anchor validation before the user can accept it. Runtime failure, cancellation, or invalid output never switches to a direct API.

MCP may be evaluated as a shared read-only tool/context protocol only if needed. ACP and MCP are communication protocols; neither is by itself an OS security boundary.

### macOS agent isolation research (reviewed 2026-10-14)

No current runtime has a verified Code Atlas boundary. Codex's app-server documents restricted readable roots for `readOnly`, but the same surface also exposes `command/exec`; that mode therefore does not establish the task's no-shell/no-build requirement. ACP provides terminal methods and file operations as protocol capabilities, but withholding client-side methods does not prove that an agent's own tools cannot access the host. Keep all candidates unavailable until both filesystem confinement and command/tool restrictions are exercised against the selected version. See [Codex sandbox read access and command execution](https://developers.openai.com/codex/app-server), [ACP terminals](https://agentclientprotocol.com/protocol/v1/terminals), and [ACP tool calls and permissions](https://agentclientprotocol.com/protocol/v1/tool-calls).

The clearest macOS boundary candidate to prototype is a per-run Linux VM that exposes only a newly materialized reviewed snapshot directory through a read-only `VZSharedDirectory`. This can omit the live checkout and `.git` from guest-visible mounts, but it does not itself prevent a guest process from running shell/build commands or reaching the network. The runtime must still have its command, web, and unapproved MCP tools removed and those restrictions tested; egress, cancellation, crash cleanup, and stage deletion also need explicit checks. Apple's Virtualization framework requires the virtualization entitlement and architecture-matched Linux guest assets, so startup time, bundle size, updates, and supported Mac architectures need a separate packaging decision. See [VZSharedDirectory](https://developer.apple.com/documentation/virtualization/vzshareddirectory), [running Linux in a VM](https://developer.apple.com/documentation/virtualization/running-linux-in-a-virtual-machine), and [adding the Virtualization entitlement](https://developer.apple.com/documentation/virtualization/adding-the-virtualization-entitlement-to-your-project).

**Next evidence:** run a no-agent boundary spike with a synthetic stage. Prove writes fail, `.git` and unrelated host paths are absent, arbitrary shell/build execution is denied by the chosen runtime configuration, and cancel/crash cleanup removes per-run state. Keep the user-requested Codex, Claude Agent, and Antigravity routes unavailable until each also passes its own version, terms, lifecycle, and runtime-tool checks.

### Reuse decisions and current first-party surfaces (reviewed 2026-10-13)

Prefer a maintained, vendor-supported integration surface when it meets the product contract. Use a shared protocol such as ACP only where the exact runtime/adapter supports the needed lifecycle and permissions. Do not drive a vendor's interactive terminal UI, and do not create a new agent loop merely to normalize providers. Compare release activity, license, reproducible adoption signals, platform support, and capability evidence; stars or protocol participation alone do not establish safety or fit.

## Speech is a separate modality

TTS remains under [t18 optional narration](../kata-tasks/18-optional-narration.md). The speech catalog has its own provider/model capability record, request review, voice/language limits, key/terms/usage disclosure, cancellation, local cache, and audio validation. A text adapter's support for Gemini/OpenAI/Anthropic does not imply that it can synthesize speech.
