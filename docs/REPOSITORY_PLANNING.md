# Repository planning contract

## Current state

Repository planning is incomplete. Source now contains a transport-independent planning context, JSON result contract, local validator, registered local preparation command and separate Codex/Claude planning review/send commands. Native senders now publish unaccepted local plan drafts, with registered metadata discovery, source-revalidating load and explicit discard commands. The app now has an agent-only question/source chooser, both planning review/send callers and a saved-plan reader with source citations. Accepted plan revisions, linked notice resolution, multi-request orchestration and native acceptance remain incomplete. Claude planning dispatch remains unavailable behind the empty runtime qualification registry. The existing call-based reading planner remains a separate feature. The [operation matrix](AGENT_OPERATION_PARITY.md) records bounded Codex planning as **Source**, while Claude stays **Missing** behind native qualification; neither is accepted production support.

The implementation is in [repository_plan.rs](../src-tauri/src/repository_plan.rs), [its local commands](../src-tauri/src/repository_plan_commands.rs), [the native draft store](../src-tauri/src/repository_plan_store.rs) and [the typed client](../src/lib/repositoryPlans.ts). No new agent loop, model catalog, API credential flow or service was added. No tests, builds, app launches, CLI/SDK probes, logins or model requests ran for this change.

## One bounded planning unit

`prepare_repository_plan_context` accepts one `input` object with `projectId`, `snapshotId`, `question` and `selectedPaths`. It requires an open project and an immutable snapshot belonging to it. The learning question contains 8–300 characters. Source selection uses the shared chapter evidence loader: 1–12 distinct captured files, at most 250,000 source bytes, integrity checks and bounded local index evidence. Planning additionally rejects ineligible captured paths and secret-like selected contents. The encoded prompt/schema contract is limited to 512,000 bytes.

The result shows the exact selected source, question, filtered symbols/relationships, index status/truncation, prompt, schema, byte count and approximate input token count. `contextSha256` binds the planning data and prompt version; `requestBodySha256` binds the complete transport-independent prompt/schema envelope. Neither is a source consent, stored agent review or inference authorization. The command starts no agent and sends nothing to a provider.

The inventory digest covers sorted captured-file, skipped-path and directory records plus snapshot/capture-policy identity. Absolute repository roots are not included in model context. Coverage counts selected files, other eligible captured files, excluded captured records and unique skipped paths. Eligibility describes captured metadata; it does not establish behavior or inspect unselected contents. A partially captured repository stays visibly partial. Preparing all eligible files still does not establish that they have explanations.

## Native agent request reviews

The registered `build_codex_repository_plan_review` and `build_claude_repository_plan_review` commands prepare distinct `repositoryPlan` operations. Their strict nested inputs contain project/snapshot, learning question and selected paths, plus the chosen agent's settings. They reuse the existing native pending-review store and agent contract builder. Neither starts inference, reads an API key, grants consent or authorizes a planning sender. The app planning flow now calls the typed review helpers through the existing Codex and Claude setup/configuration components.

| Agent | Native identity and settings |
| --- | --- |
| Codex | Configured installation path comes from native status. Review records selected model/effort and fixed `never` approval; runtime/model/account qualification remains separate. |
| Claude Agent | An opaque current native connection supplies executable/account/catalog identity. Supported model/effort, fixed `dontAsk` and turn bounds are checked against that observation. Connection replacement/refresh invalidates publication and insertion caps expiry to that connection. This is still an observed connection, without qualified inference. |

`generationConfig.repositoryPlan` retains the exact question, capture status, inventory/context/planning-contract digests, coverage and index status. The review fingerprint also binds the complete agent contract, selected source and settings. Source-only rebuild helpers require the correct agent/endpoint/purpose/contract and an unexpired review, rebuild from native source/runtime observations, and compare every review field after retaining its original ID and expiry. Rebuilding cannot renew admission. The native planning senders now use these preflight helpers. Active result rebuilding retains the same ID/expiry under native operation ownership; it cannot admit a fresh run after expiry.

The shared result bridge checks review/fingerprint/model identity, bounds the response, reopens the same native context and calls the independent plan validator. Its provider/model/usage labels come from the native dispatch result; this helper alone cannot prove which agent produced arbitrary JSON. It saves nothing. The native senders now own preflight, active result validation and progress/cancellation; accepted plan history, linked notice resolution, complete recovery and native acceptance remain open. Existing chapter/range/Git senders reject the distinct planning purpose. The direct API command boundary now checks backend and operation before fingerprint removal, source revalidation, credential loading or consumption, preserving a foreign agent review after a wrong-command attempt. These are unexecuted source changes.

## Native planning execution — unexecuted source

Both native commands accept one strict `input` containing only `reviewId`, `fingerprint` and explicit `consent`. Source, model, effort, approval and runtime identity come from the original native review. A different backend or operation fails before review consumption. Expired admission, changed context/settings, a closed project or failed journal write prevents worker dispatch. No direct API key, API request encoder or provider fallback enters either path.

| Command | Native lifecycle |
| --- | --- |
| `send_codex_repository_plan_request` | Reuses shared Codex preflight, native account/model admission, staged reviewed files and app-server. Holds process/operation ownership through pure result validation. The admission clock includes blocking queue/setup, generation and validation; it is checked before inference, during generation and around validation/publication. The final publication check is serialized with cancellation. Dropping the async owner cancels a queued/running worker; a worker panic shuts the manager down and retains recovery. |
| `send_claude_repository_plan_request` | Requires the same release-owned qualified runtime as other Claude senders, then uses its revocable connection lease, reviewed settings, stdin context, managed worker, active source rebuilding and guarded publication. Refresh/forget/cancel/owner drop still invalidate a result. The qualification registry remains empty: every current invocation rejects before consuming or sending the review. |

Only the already admitted same native run can finish after ordinary review expiry; rebuilding cannot renew consent or launch another run. Codex's result access exists only inside its manager-owned validation callback. That callback only prepares an in-memory candidate: cancellation/deadline can still reject it. A separate publication callback runs after the final ownership check under the same lock used by cancel. It saves the unaccepted draft; a cancel arriving after publication starts cannot retract that draft. The store publisher fails if its lock is busy rather than queuing behind a source-revalidating reader under an agent ownership lock. Claude saves under its existing revocable publication guard. Existing Codex chapter/range/Git senders reuse the extracted preflight and plain runtime wrapper; their separate result preparation remains outside that callback and still needs its own lifecycle acceptance.

The senders return `RepositoryPlanPreview`: original review/fingerprint, native backend/model metadata, unaccepted locally validated plan and `recoveryOperationId`. Successful native publication now sets `savedLocally: true` and writes an unaccepted plan record. It writes no chapter or accepted plan history, marks no file explained and retains the planning interruption notice even after success. A failed save returns a local-storage error with recovery guidance. If directory synchronization fails after publication, the error explicitly says a plan may already exist; inspect saved plans before generating again. Existing cancellation commands/events are reused with the review ID. The app now calls both senders and can reopen saved drafts. Codex bounded planning is Source in the operation matrix; Claude remains Missing because runtime admission is unavailable. Runtime/account/isolation and workflow behavior have not been exercised.

## Planning interruption scope — source groundwork

The shared journal can now retain a `repositoryPlan` request for either agent. Its optional `repositoryPlan` field records the original learning question and descriptive native review scope: inventory/context/contract digests, capture status, coverage and index status. Project, snapshot, backend and distinct selected paths remain in the enclosing record. It retains no assembled prompt, source contents, agent connection/settings, credentials or consent. Native planning senders write this record before starting their worker. They retain it on success and failure because explicit app review/discard and notice resolution remain pending. Discarding a stored draft alone does not remove a separate interruption notice.

Native journal validation requires the planning purpose and scope together, an agent backend, one to twelve selected files, consistent coverage counts, bounded original question and valid digests. Mixed chapter/section/range/Git targets fail. Older non-planning records still omit the optional field. Reopening a planning notice through `load_interrupted_generation_scope` prepares the exact original question and immutable selection locally, compares the entire scope, then checks that the journal entry did not change during the read. Changed inventory, context, index, coverage or capture status cannot silently produce a different request. This grants no runtime, model request or consent.

The app labels planning notices separately and shows the original question. Review first revalidates the native journal scope and unchanged notice identity, then opens Learning plans at the original project/snapshot with the original question, selected files and backend. A user must explicitly confirm checking earlier saved plans before choosing the original agent and preparing a fresh request. No connection, settings, consent, or model run is restored automatically; no overview, chapter, Git or API flow is substituted. Earlier drafts are inspectable in Learning plans after closing the chooser. Complete linked notice resolution, immutable accepted plan revisions and native recovery acceptance remain pending.

## Generated plan and local validation

The separate plan result contains `contextSha256`, a specific title, 1–24 steps and 1–8 anchored unknowns. Each step has a short local ID, learning question, primary source path, prerequisite IDs and one grounded claim. Questions end in a question mark. Prerequisites may name only earlier steps, preventing forward references, self-dependencies and cycles. They represent a learning order; they cannot prove an execution or data-flow edge.

Each claim uses the existing chapter evidence schema. The validator reuses the chapter quote/identifier/relationship checks rather than accepting invented anchors. Exact unique quotes must exist in the selected captured bytes and name the identifiers stated in the rationale. Relationship IDs must come from the reviewed resolved evidence and pass the existing independent source/index checks. Every primary path must occur in that step's verified anchors. Unknowns must be labeled inference with a bounded basis and their own evidence. Unsupported module, protocol, language and runtime boundaries cannot become proven relationships because a model suggests an order.

Validation reopens the native preparation input and rejects changed inventory, context, request contract or selected index evidence. It bounds response bytes, rejects malformed JSON, unknown/duplicate typed properties, invalid IDs and excessive collections. Native code assigns draft, step, claim and anchor identities; model local IDs cannot become global destinations. Planned paths come from the steps' validated primary files. Merely citing a supporting file or an unknown does not give it a dedicated step: cited paths are listed separately, and selected files without a primary step stay omitted. These sets are computed locally, independently of any model coverage claim.

The validator returns unaccepted data. It does not persist anything, accept a chapter, mark a file explained or validate human comprehension. Agent/account/model provenance must come from the native agent dispatcher; the local validator cannot identify which tool produced arbitrary JSON. Questions and pedagogical quality still require review.

## Durable unaccepted drafts — unexecuted source

Both native planning senders prepare a bounded storage candidate after active review rebuilding and independent result validation. Publication uses the original agent ownership guard. A record stores the original strict proposal, canonical plan, descriptive scope, selected paths, review/fingerprint/model/usage labels and only the agent's effective effort/approval/turn settings. Exact quotes remain in the proposal and canonical citations. Full source files, assembled prompts, executable/account/connection metadata, credentials and reusable consent are not stored. Recorded backend/settings labels are local dispatch metadata, not tamper-proof proof of which account or model produced a file.

Records live under native app data in `repository-plans/<SHA-256 of project ID>/<plan UUID>.json`. Renderer commands cannot supply a storage root. Publication bounds a record to 2 MiB, a project to 128 canonical records and 64 MiB, and scans to 512 directory entries. All regular entries count toward byte/entry limits, including unexpected or leftover staging files. Records use a private, create-new staging file, complete write/file synchronization and a no-overwrite hard link before directory synchronization. Conflicting identities, full storage, unexpected nonregular entries and uncertain durability preserve existing data and the original interruption notice. Stale staging/unexpected files are not silently pruned. These are source invariants awaiting native filesystem/crash acceptance, not a claim of verified durability or resistance to a hostile local filesystem.

| Local command | Contract |
| --- | --- |
| `list_repository_plan_drafts(projectId)` | Open-project ownership and bounded metadata discovery. Damaged/oversized/incompatible regular records appear as unavailable entries. A successful list does **not** validate source evidence. |
| `load_repository_plan_draft(projectId, draftId)` | Requires canonical native identity/project ownership and bounded strict JSON. Rebuilds the original context, compares the entire saved scope, replays the original proposal and compares every canonical semantic field. Retains the saved plan/step/claim/citation IDs and creation time. Changed source, inventory, index, coverage, question or proposal cannot silently become a different plan. |
| `discard_repository_plan_draft(projectId, draftId)` | Explicitly removes only the selected canonical regular local record, including damaged JSON. Nonregular files and unrelated history/notices remain preserved. Missing records are idempotent. |

Readers use the shared no-follow file opener; on Unix it also opens nonblocking so a FIFO replacement cannot block before handle metadata is checked. A returned detail omits the raw proposal and exposes recorded settings plus the original question/scope. Loading grants no new runtime connection, request review or consent. Native IDs survive reopening; no new step/citation destinations are generated for a saved draft. Deserialization alone cannot qualify evidence: the full load must replay validation.

App callers, saved-draft review and exact fresh-review routing from recovery are now present in source. Linked notice resolution, accepted plan revisions and multi-unit orchestration remain incomplete. Codex bounded planning is Source; Claude still rejects dispatch behind the empty qualification registry and remains Missing. No tests, builds, app launches, CLI/SDK probes, logins or model requests ran. Deferred storage/publication/reload cases are tracked in `xymb`.

## App flow — unexecuted source

In Guide, choose **New learning plan**, write a question and select captured source. The form shows selected paths, total bytes and bounded search results; it rejects empty/oversized selections without truncating them. **Choose agent and review request** opens the dedicated coding-agent chooser. Codex and Claude use their existing setup, current model catalog, vendor-specific reasoning controls and fixed explanation approval policy. Claude also retains its turn limit. Source/question stay fixed inside the agent dialog; close it to edit the plan form. Direct APIs and manual handoff are not substituted for planning.

Preparing a review remains local. Starting generation requires the exact source/prompt/settings review and fresh consent. Existing progress/cancel, review expiry, native identity revalidation and owner cleanup apply. A validated saved response shows its title/step/omission counts and remains unaccepted. Closing/switching/cancelling cannot delete an already published plan. Even a lost or unwanted reply refreshes saved-plan discovery and recovery; a storage/identity failure tells the user to inspect earlier drafts before another request.

**Saved drafts** lists metadata. Opening one calls the native evidence-revalidating load before displaying rationales or enabling source actions. The reader has a step selector, **Back**, **Next**, exact source excerpts/citations, inference bases, prerequisite numbers, original snapshot/settings, explicit partial-capture/index/coverage limits and omitted/unknown files. **Explain this file** enters the existing chapter backend chooser with the primary file and cited support; it is available only for the currently selected snapshot. Earlier-snapshot plans open their original source citations first. No autoplay, automatic chapter generation, chapter acceptance, plan acceptance or reading-progress mutation is implied.

Discard requires an explicit local confirmation and preserves separate recovery notices. Damaged regular records retain an unavailable row and discard action. Refresh and superseded loads use scoped lifetime guards; native load remains authoritative. The previous static call planner stays accessible under **Build a static call reading order** and reopens for its existing journey return-focus route. Source styles use wrapping layouts and visible keyboard focus; keyboard/VoiceOver/200% reflow/contrast/motion checks remain unexecuted acceptance work.
