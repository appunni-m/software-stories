## User outcome
The user can choose a supported coding-agent backend—such as Codex, Claude Code, Gemini CLI, or Google Antigravity—to investigate a repository snapshot and produce a source-grounded draft, while Code Atlas keeps the working copy and the user in control. The catalog is extensible, but it lists a runtime only after the exact supported integration surface and safety boundary are verified.

Automatic Codex and Claude Agent integration is priority 0. The [required operation matrix](../AGENT_OPERATION_PARITY.md) defines the exact shared workflows and current missing adapters. Both must work without mandatory direct API credentials. Manual copy/import is interim transport and cannot complete this task or replace either automatic adapter.

## Contract
Add distinct agent-runtime candidates for Codex, Claude Code, Gemini CLI, and Google Antigravity through a supported programmatic surface. Evaluate ACP (including registry entries and whether each implementation is native or a wrapper) as the common session protocol; use it only when the exact maintained adapter supports the required events and permissions. Otherwise use that product's documented SDK, app-server, or headless interface. Evaluate the Antigravity SDK and CLI as separate surfaces; use a CLI embedding only for account plans and terms that permit it. Never automate a terminal TUI, reverse-engineer private APIs, or implement another agent loop. If Code Atlas needs to expose reusable tools/context, evaluate one read-only MCP server as the established tool protocol and record each runtime's configuration and capability differences; MCP is not a security boundary. Maintain a dated, versioned operation-to-runtime compatibility matrix for repository investigation, file/overview chapters, section regeneration, on-demand Code Lens explanation, and PR guide/change explanation workflows. For each workflow/runtime pair it records the exact integration surface and version, adapter provenance, account/terms eligibility, auth method, ACP support status or SDK/app-server/CLI rationale, supported lifecycle events (progress, permission, cancel, and resume where available), capability/permission limits, usage disclosure, adoption/maintenance evidence, and tested behavior. A new runtime can be added by adding a reviewed matrix entry and corresponding adapter evidence; candidate status does not promise availability.

Treat ACP as a communication protocol, not as a security boundary. Verify the selected runtime's actual filesystem, shell, MCP, network, and write capabilities for each supported version; use an OS sandbox around the staged snapshot when the runtime cannot enforce the complete read-only boundary itself.

An agent explanation runs only on an app-created staging area containing the user's reviewed immutable snapshot files. Never pass the live checkout or `.git` data. The runtime must have a verified read-only permission mode, no shell/build execution, no web or unrelated MCP tools, and no access to paths outside the approved staging area. If an adapter cannot enforce that boundary with supported agent controls or an OS sandbox, mark it unavailable for repository explanation. Use only each product's documented login/authentication flow; never extract browser sessions or reuse an account credential through an undocumented route.

Separate provider control traffic from agent-tool egress. A selected runtime may use only its documented authentication and model endpoints through an app-managed provider broker or an OS-enforced, destination-restricted egress path fixed by the reviewed backend integration. The agent must not gain arbitrary network access, browser/web/search/fetch tools, or unrelated MCP tools; agent approval settings cannot widen the endpoint allowlist. Authentication/setup sends no repository context. Model requests may include only reviewed staged context and occur after explicit run consent. Test that the selected provider path works and unrelated destinations/tools fail. If the pinned runtime cannot separate provider traffic from agent-controlled egress, it remains unavailable.

Before a run, show the agent/runtime version, exact staged files, provider/account path, terms and data-use disclosure, permission boundary, cancellation behavior, and that a multi-step run may make multiple model calls or incur usage. Require explicit run consent. Agent output is untrusted, must pass existing local schema/evidence validation, and cannot be accepted without Chapter Studio review. Agent errors or cancellation never silently invoke a direct API provider.

Provide per-runtime configuration rather than a single agent name selector. In Settings, users can choose the agent runtime and configure its supported model, reasoning effort/depth, approval policy, and other documented runtime-specific options. Save non-secret defaults per runtime on this Mac and allow a deliberate per-run override. Keep credentials in the documented secure credential store, separate from these preferences. The run review shows the effective runtime/version and every effective setting that will be passed to the adapter.

Populate configuration choices from the pinned, verified runtime and adapter capabilities. Send the selected model identifier and exact supported reasoning/approval values through to the runtime; do not invent cross-runtime options or silently ignore a selection. If a runtime does not expose a setting, mark it unsupported and explain that in the UI. Distinguish the user's mandatory consent to send the reviewed context from approvals requested by the agent during its run. Offer only approval policies whose semantics and permission scope have been verified for that exact runtime. A chosen approval policy may govern pre-approved reads within the reviewed immutable staging snapshot, but can never authorize writes, shell/build execution, arbitrary network destinations, browser/web/search/fetch tools, `.git`, or reads outside the approved snapshot. The separately reviewed provider authentication/model path is fixed by the adapter and cannot be broadened by an agent approval or tool call.

Changing runtime, version, authentication account, model, reasoning option, approval policy, runtime-specific setting, staged context, or disclosure invalidates the pending run review and requires a fresh review and explicit consent.

Availability is conditional on the selected product surface, account terms, and tested version. For example, Gemini CLI ACP and Plan mode require pinned-version verification; its current documentation marks `--approval-mode=plan` as under development and not fully functional, so do not treat it as a proven read-only control. Codex app-server documents a `readOnly` sandbox policy with restricted readable roots and a ChatGPT-plan OAuth path for open-source clients; still verify app attribution/distribution eligibility and prove that command/build execution is unavailable. A runtime is disabled for repository explanation until its supported controls and/or an OS sandbox establish the full boundary. Use each vendor's documented authentication rules; never extract browser sessions or reuse an account credential through an undocumented route.

As of 2026-10-13, Anthropic's account-path guidance is inconsistent across its official pages: the Agent SDK overview says a third-party product may not offer `claude.ai` login or subscription limits without prior approval, while the Help Center updated 2026-10-07 says third-party apps can use Claude plan limits and Max/Team plans include monthly API credits. Do not expose subscription-based Agent SDK authentication until Anthropic reconciles or approves the exact integration. API-key or documented cloud-provider authentication remains the documented baseline. For Antigravity, Google's recommendation to use Gemini Enterprise or Google AI Studio API keys for third-party coding agents using Gemini does not automatically authorize embedding Antigravity SDK, ACP, or headless CLI; assess terms for the exact runtime/account combination, and never use a consumer Antigravity login.

Prefer a vendor's maintained programmatic surface when it fits this contract: for example, evaluate Codex SDK/app-server and the Claude Agent SDK before wrapping their CLIs. Use “Claude Agent” (preferred) as the Anthropic-backed option label; Anthropic does not permit “Claude Code” or “Claude Code Agent” branding for an embedded Agent SDK integration. The SDK is still the Claude Code-powered agent loop and is separate from the Claude direct API. Google documents Antigravity as an official Python SDK plus an interactive CLI TUI and a distinct headless mode. Treat the SDK, ACP binary, TUI, and headless command as separate candidates; never automate the TUI. The SDK includes a native runtime and filesystem/command/web tools, so pin the exact SDK/runtime version, verify packaged macOS architectures and bundle impact, explicitly remove write, shell, web, and unapproved MCP capabilities, and test the resulting boundary. Google's FAQ says consumer Antigravity login cannot be used by third-party applications and that wrapping `agy -p` is unsupported on consumer plans; it recommends Gemini API-key or Gemini Enterprise auth for third-party agents. Confirm that the exact SDK/ACP/API-key or Enterprise route is permitted under current terms before exposing it. This does not change the separately reviewed Gemini direct API option in t28.

## Acceptance criteria
- The catalog distinguishes Model APIs from Agent runtimes. It treats Codex, Claude Agent (powered by Claude Code), Gemini CLI, and Google Antigravity as candidates, and lists each only when its exact version, official programmatic surface, terms/account path, and capability boundary have been verified. Anthropic's display-name guidance is followed; the embedded Agent SDK is not branded “Claude Code.” Antigravity SDK, ACP binary, TUI, and headless CLI are evaluated separately; a CLI surface is unavailable on plans that prohibit third-party embedding.
- M7 cannot close until the user-requested agent choices have a selectable, tested route: Codex; Claude Agent powered by Claude Code using Anthropic-approved UI naming; and Google Antigravity through an explicitly permitted, tested API-key or Enterprise integration path. If current terms or runtime safety make one unavailable, record the reason and leave M7 open; do not count “unavailable” as satisfying the requested backend. Gemini CLI is an additional candidate, not a substitute for the named choices.
- Gemini CLI uses a pinned, tested ACP mode when supported; the compatibility matrix records its exact launch flag and status. For Codex, Claude Code, and Antigravity, evaluate the exact ACP registry adapter and its provenance; use it only if it passes the same support and safety checks. Otherwise use that product's documented SDK, app-server, or headless interface. Unsupported or experimental surfaces remain unavailable until their required behavior is verified.
- Record the exact ACP registry snapshot for Codex, Claude Agent, Gemini CLI, and Antigravity with adapter/package version, distribution, license, authorship/provenance, and whether the implementation is a native runtime or wrapper. For Antigravity, evaluate the registry's Google-distributed `antigravity-acp` binary independently from the Python SDK and CLI; registry presence alone does not grant product-embedding terms or prove safety.
- The matrix contains a dated, source-linked decision for every evaluated surface, including whether ACP is supported and why it was selected or rejected, or which documented SDK/app-server/headless surface is used instead. The record includes maintenance/adoption evidence and does not confuse protocol popularity with verified runtime capability.
- The surface decision prefers a supported vendor SDK/app-server when it fits, and documents why ACP or another adapter is used otherwise. For Antigravity, the record separately assesses SDK and CLI, SDK native-runtime/platform packaging, read-only tool configuration, and whether current account terms permit Code Atlas to embed it; official SDK availability alone is not treated as terms approval.
- ACP integrations identify whether the runtime speaks ACP natively or relies on a wrapper/adapter, and pin the tested runtime and adapter versions. If a shared MCP tool/context server is used, each runtime's configuration and actual allowed tool set are tested; MCP alone never satisfies the filesystem or process-isolation boundary.
- Each workflow/runtime pair is either marked supported with a fixture acceptance run or clearly unavailable with a reason; selecting a runtime never silently switches to another runtime or a direct API.
- Agent launch uses only the explicitly selected executable/runtime and its documented auth; no secrets are copied into prompts, logs, or exported guides. New agent backends require an explicit catalog entry and runtime-specific adapter tests before they can be selected.
- The agent receives only reviewed immutable snapshot paths in an isolated staging area; it cannot read other repository paths, mutate the real checkout, access `.git`, or run repository scripts/builds. Verify those restrictions against each actual supported runtime, not only a protocol stub or its advertised read-only mode. A runtime without a verifiable boundary is disabled for this workflow.
- The UI discloses agent-controlled model selection and possible multi-call billing where exact request count or cost cannot be known in advance; no API-provider fallback occurs.
- Settings provide a selectable runtime and persist its supported model, reasoning effort/depth, approval policy, and documented runtime-specific options as per-runtime defaults, with explicit per-run overrides. Secrets are stored separately from preferences.
- The run review shows the exact effective configuration. Model IDs and reasoning/approval values are selected from the pinned runtime's verified capabilities and are passed through unchanged or mapped by documented adapter rules. Unsupported options are clearly unavailable; no selection is silently ignored or fabricated.
- Approval configuration is distinct from mandatory pre-run context consent. Its choices state which in-scope actions may proceed automatically and which require user approval. Every mode preserves the immutable staging boundary and denies writes, shell/build execution, arbitrary network destinations, browser/web/search/fetch tools, unrelated MCP tools, `.git`, and out-of-snapshot reads. Only the selected adapter's reviewed authentication/model endpoints may use the separately enforced provider-control path; setup sends no repository context and inference requires fresh run consent. Verify an allowed provider request and denied unrelated destinations/tools; if the pinned runtime cannot enforce this separation, it is unavailable.
- Changing any effective runtime configuration or reviewed context invalidates the previous consent and requires a new review.
- The user can observe progress, cancel a run, and inspect the resulting draft. Cancellation, runtime failure, or invalid evidence leaves accepted guide history unchanged.
- Claims from agent output are checked against local snapshot anchors and cannot be accepted automatically.
