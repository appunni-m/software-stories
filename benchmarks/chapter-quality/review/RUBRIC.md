# Chapter quality review

This is the human quality gate for the repository-level chapter benchmark in [Kata t14](../../../docs/kata-tasks/14-chapter-quality.md). It evaluates whether a chapter explains the selected file from the pinned source. Schema and citation validation establish payload shape and source identity; neither proves that the explanation teaches the file's behavior. The generation prompt and structural checks are in [`provider.rs`](../../../src-tauri/src/provider.rs) and [`chapter_generation.rs`](../../../src-tauri/src/chapter_generation.rs); the payload contract is in [`CHAPTER_SCHEMA.md`](../../../docs/CHAPTER_SCHEMA.md).

## Review rules

1. Review the exact corpus revision and captured source bytes named by the report. A source hash identifies bytes; it does not prove a claim is true.
2. For each claim, compare its wording with the cited source span. A citation that only repeats a symbol name, or a broad quote that does not show the described operation, does not support the claim.
3. Mark every applicable criterion `pass` or `fail`. `notApplicable` is allowed only when the corpus manifest declares that criterion inapplicable for this case; record that justification in the criterion's `reason`. Do not use it to excuse missing or difficult evidence. The reviewer records claim IDs and source references for every pass and fail. `unsupportedClaims` is mandatory for every case and cannot be `notApplicable`.
4. A case passes only when chapter schema/evidence validation passes and every applicable rubric criterion passes with no unsupported factual claim. One failure makes the case fail. The report passes only when every manifest case has a final passing outcome and all report provenance is complete.
5. Keep the first review attempt when repairing a chapter. Record a new `repaired` attempt and its artifact digest; do not replace the failed result. A repair passes only after the same failed criteria are re-reviewed.
6. A human reviewer reads source and chapter independently. Provider self-critique is not a review. Do not send private benchmark source to a provider without explicit consent. Keep reports and chapter artifacts local; they are not product telemetry.

## Binary criteria

The corpus manifest fixes applicability per case and names expected source facts as repository-relative path plus exact source quote. Those expectations give reviewers a stable target without requiring equal chapter length or a fixed number of sections.

| Criterion key | Pass only when | Fail when |
| --- | --- | --- |
| `responsibility` | The chapter says what this selected file itself is responsible for, in concrete terms, and backs it with a target-file span. | It could describe many files, substitutes the repository's purpose for the target's role, or lacks target-file evidence. |
| `declarations` | Each applicable key declaration, function, type, or configuration key named by the manifest is described accurately; the chapter distinguishes a declaration from its consumers. | It omits a key declaration, lists names without explaining their role, or invents a consumer. For a one-declaration file, that declaration may be the whole criterion. |
| `executionPath` | When the source has multiple steps, branches, or calls, the chapter explains their order/data handoff and only calls a relation resolved when the selected source/index proves it. | It says merely “processes the request,” reverses/skips a behaviorally important step, or presents an import, name, or static edge as proof of runtime execution. Mark N/A only for a case whose manifest has no multi-step path. |
| `applicableBehavior` | Every behavior question marked applicable in the manifest is answered accurately: inputs, outputs, transformations, state/side effects, and error paths as present. Short files pass with concise answers to only their applicable questions. | It omits a material applicable behavior, gives an outcome not shown by source, or paraphrases the signature without explaining what the body/value does. |
| `relatedContext` | When selected callers, dependencies, or tests exist, the chapter describes the relevant context accurately and names relationship type/confidence where provided. Otherwise it states the evidence boundary without claiming none exist globally. | It invents a caller/test/dependency, misstates a relationship, or treats absent/unselected context as proof of absence. |
| `citationPrecision` | Each factual claim has an exact captured anchor whose span directly supports the complete claim; target-file claims include target-file evidence. | Any factual claim is uncited, cites an unrelated/overbroad span, or makes the reader infer the connection that the claim fails to state. |
| `uncertainty` | Facts visible in the selected source are stated directly; inferences and limits about runtime, production callers, deployment, or unselected code are labeled and bounded. | It states unobserved runtime/business behavior as fact, hides a necessary inference, or turns an evidence hash into semantic proof. |
| `unsupportedClaims` | No claim exceeds the captured source and explicitly selected index/context. | Any claim asserts behavior, caller, side effect, error handling, or production use not established by its cited evidence. This is a zero-tolerance failure. |

`findings[]` use stable failure categories: `generic`, `missing_responsibility`, `missing_declaration`, `missing_flow`, `missing_applicable_behavior`, `missing_related_context`, `weak_citation`, `unsupported_claim`, `uncertainty_missing`, or `other`. Each finding has `category`, `claimIds`, `sourceRefs`, and `description`. A `sourceRef` contains `path`, the matching lowercase SHA-256 `sourceSha256`, inclusive `startLine` and `endLine`, and exact `quote`; use an empty `claimIds` only for a file-wide omission. Add at least one source reference and affected claim ID when the failure concerns a factual claim. `failureCategories` is the deduplicated set of categories attached to a failed case or attempt.

## Report contract

`REPORT_TEMPLATE.json` uses report schema v3, is deliberately incomplete, and must fail the release gate as written. Fill all top-level provenance (`corpusId`, corpus manifest SHA-256, exact `modelId` and returned `modelVersion`, current model-allowlist SHA-256, prompt version and prompt-text SHA-256, request-assembly SHA-256, generation-config SHA-256, chapter schema version, response-schema SHA-256, reviewer, and an ISO-8601 `reviewedAt`) before setting `status` to `pass` or `fail`. If the provider omits its model version, record `not-returned` explicitly. Do not substitute the rubric fixture for a corpus case or provider result.

The report has one `cases[]` entry per manifest case. Each case pins `caseId`, `repositoryId`, `targetPath`, captured `sourceHashesByPath`, the exact request-review fingerprint shown in the product, final raw `GeneratedChapterProposal` artifact path and SHA-256, `schemaValidation` (`pass`/`fail`), and final `outcome` (`pass`/`fail`). Its `factCoverage` maps every manifest `mustCover` fact ID to one or more positional claim IDs in the final artifact; a failing attempt may use an empty list to record a missed fact. Each mapping must resolve to a section claim with an exact, unique evidence quote on the expected path whose UTF-8 byte span contains the expected fact's manifest span. This is a mechanical linkage check; the reviewer still decides whether the claim accurately covers the fact. The gate checks strict proposal keys and limits, exact selected-file quotes, identifier linkage, target-file coverage, and positional claim IDs. It resolves each rubric/finding claim ID to that exact artifact. Each named criterion in `rubric` has `outcome` (`pending` in the template, otherwise `pass`/`fail`/`notApplicable`), `reason` (null except a nonempty reason for `notApplicable`), `claimIds`, and `sourceRefs`. `findings` is an array of the objects described above; `failureCategories` is the deduplicated category list, and `repairSummary` is null for an unrepaired initial result or a short description of the repair.

`attempts` is empty only in the unrun template. A completed case keeps its initial attempt and any later repair attempts in order. Every attempt has `label` (`initial` or `repaired`), `outcome` (`pass`/`fail`), `schemaValidation` (`pass`/`fail`), the batch's `modelId` and `modelVersion`, its exact request-review fingerprint, `chapterArtifactPath`, `chapterArtifactSha256`, `factCoverage`, the complete binary `rubric`, `failureCategories`, `findings`, and `repairSummary` (null for the initial attempt; required for each repair). Every repair has a new artifact path and digest. Never replace the initial artifact or its review when a repair is generated. The case's final outcome, schema status, request fingerprint, artifact, fact coverage, rubric, findings, failure categories, and repair summary must match the last reviewed attempt; earlier failure history remains in `attempts`.

## `fixture/rubric-example` (not a benchmark run)

It is not provider output, a corpus result, a test execution, or evidence that a model was called.

## Review cadence

Run and review the complete corpus before release and after changes to the generation prompt, chapter/response schema, or model allowlist. Compare reports by repository and case, model ID, prompt version, schema version, pass/fail, and failure category. Preserve each run as a local review artifact; do not overwrite the earlier report when a failure is repaired.
