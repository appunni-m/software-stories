## User outcome
The user can install a dependable Mac app, understand its requirements, and use local browsing without a provider key.

## Contract
Build distributable macOS artifacts using the chosen Tauri packaging path. Define supported macOS versions, signing/notarization, app data and cache locations, backup/export behavior, first-run permission needs, and how users remove local project metadata. Release notes state parser support, repository limits, provider model/disclosure verification date, and known limitations.

## Acceptance criteria
- A clean Mac account can install and launch the signed/notarized app without a development toolchain.
- Offline repository browsing, accepted guides, and exported guide reading work before key setup.
- Keychain permissions and local data locations are explained in product language.
- Release pipeline verifies artifact identity and bundled schema/migration versions.
- Failed install, permission denial, and disk-space conditions give recovery guidance.

## Excludes
Automatic in-app updates unless separately specified, paid backend services, and claiming provider pricing will remain unchanged.

## Done evidence
Install and exercise the release artifact on a clean supported macOS environment; verify signature/notarization, offline journey, Keychain behavior, release notes, and artifact checksums.

## Local packaging baseline
The Tauri config requests local `.app` and `.dmg` bundles using the checked-in macOS artwork and explicitly enables Tauri's hardened runtime setting. `npm run bundle:macos` writes the current Rust schema versions, runs `tauri build --no-sign --bundles app,dmg`, then checks the bundle identifier, product/version fields, embedded schema metadata, absence of an undeclared minimum-system version, and exactly one DMG. `.github/workflows/macos-package-verification.yml` is configured to run this unsigned package check for pull requests, pushes to `main`, and manual dispatch. This is a CI preflight, not a release pipeline or release artifact; no successful workflow run is recorded here, and the check does not verify a signature, notarization ticket, checksum, or clean-account install. There is no database migration series in the current file-based storage implementation, so the metadata manifest records the current chapter, visual, index, and recovery formats instead of inventing a migration version.

The packaging command did not produce an `.app` or `.dmg` in this environment. `xcode-select -p` points to `/Library/Developer/CommandLineTools`, and `xcodebuild -version` reports that full Xcode is required. The local release metadata file may be generated by the command, but there is no bundle to inspect.

Release decisions remain open: set and validate the supported minimum macOS version, and provide an Apple Developer ID signing identity/team plus notarization credentials. Tauri documents `minimumSystemVersion: null` as removing both the plist deployment floor and the `MACOSX_DEPLOYMENT_TARGET`; this is not a compatibility claim. Do not infer support from Tauri's default or the build host. Direct distribution requires Developer ID signing and notarization; Apple requires hardened runtime and a secure timestamp for notarization. The build host has neither full Xcode nor release credentials, so clean-account install, offline use, Keychain behavior, and notarization remain unverified.

The current storage path, optional Keychain behavior, export limits, and removal steps are documented in [Local data and permissions](../LOCAL_DATA.md). That guide states that Offline export is not a complete backup and that removing a project from Recents does not delete its stored data.

References: [Tauri macOS bundle configuration](https://v2.tauri.app/reference/config/#macconfig), [Tauri macOS signing and notarization](https://v2.tauri.app/distribute/sign/macos/), and [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
